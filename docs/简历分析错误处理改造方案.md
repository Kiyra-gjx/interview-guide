# 简历分析错误处理改造方案

## 1. 改造目标

当前简历分析链路存在两个核心问题：

1. 后端会把 AI 原始异常、JSON 解析异常、额度异常等技术细节直接暴露给前端。
2. 异步分析任务失败后缺少结构化失败元数据，前端只能展示一段不可控的原始错误文本。

本次改造目标：

1. 后端统一把 AI / 结构化输出异常翻译为用户可理解的错误文案。
2. 异步分析失败时持久化结构化错误信息，而不是持久化原始堆栈文本。
3. 前端根据错误码和可重试信息展示友好失败态，避免直接暴露底层异常。
4. 保留后端日志中的技术细节，确保排障能力不下降。

## 2. 改造范围

本次只覆盖“简历上传后异步分析”链路，不扩散到面试评估和知识库向量化链路。

涉及模块：

1. 后端错误翻译与简历分析服务。
2. 简历分析异步消费者与简历实体持久化字段。
3. 简历详情 / 历史接口返回字段。
4. 前端简历详情页失败展示。

## 3. 实施顺序

必须严格按照以下顺序推进：

### 阶段一：后端错误翻译基础能力

目标：

1. 建立统一的 AI / 结构化输出错误分类能力。
2. 停止把 `e.getMessage()` 直接拼到用户可见文案中。
3. 简历分析失败时不再伪造“失败分析结果”，而是明确抛出业务异常给异步链路处理。

计划变更：

1. 新增统一错误翻译对象与翻译器。
2. 补充缺失的 AI 错误码，覆盖额度不足、结构化输出格式异常等场景。
3. 改造 `ResumeGradingService`，把内部错误日志与用户可见错误彻底分离。

验收标准：

1. `ResumeGradingService` 不再返回包含原始异常文本的兜底分析结果。
2. AI 返回非法 JSON、额度不足、鉴权失败、超时等场景能得到稳定的用户文案。
3. 原始异常只保留在日志中，不进入接口返回或持久化字段。

### 阶段二：异步失败元数据持久化

目标：

1. 给简历分析失败增加结构化错误码与是否可重试标记。
2. 失败记录落库时保存“安全文案 + 错误码 + 可重试标记”，不保存原始技术细节。

计划变更：

1. 扩展 `ResumeEntity` 增加分析失败错误码与可重试字段。
2. 改造 `AnalyzeStreamConsumer`，在异步失败时写入结构化失败信息。
3. 改造 `ResumeDetailDTO`、`ResumeListItemDTO`、相关 mapper / service 返回新增字段。
4. 改造重新分析逻辑，重置新增失败字段。

验收标准：

1. 简历分析失败后，数据库中的错误信息为用户友好文案。
2. 接口能返回 `analyzeErrorCode` 与 `analyzeRetryable`。
3. 再次发起重新分析时，旧的失败信息会被清空。

### 阶段三：前端失败态展示

目标：

1. 前端不直接展示后端原始错误串。
2. 根据错误码与是否可重试信息展示更稳定的失败提示和操作引导。

计划变更：

1. 扩展前端 `history` 类型定义，接收新的失败元数据。
2. 改造 `AnalysisPanel` 的失败态文案与展示逻辑。
3. 保留“重新分析”按钮，仅在可重试或未知场景下继续展示。

验收标准：

1. 简历分析失败卡片只展示友好提示。
2. 不再把 `analysis.summary` 中的技术异常直接渲染给用户。
3. 额度不足、API Key 错误、结果格式异常等场景能看到区分后的提示。

## 4. 提交策略

提交必须按阶段拆分，不允许把全部修改压到一个提交中。

计划提交顺序：

1. `文档：新增简历分析错误处理改造方案`
2. `重构：统一简历分析错误翻译与失败抛出`
3. `重构：持久化简历分析结构化失败信息`
4. `优化：前端友好展示简历分析失败状态`

## 5. 风险与注意事项

1. 项目当前依赖 `spring.jpa.hibernate.ddl-auto=update`，新增字段会在本地自动补列，但已有脏数据可能仍保留旧错误文本。
2. 本次不处理历史旧数据清洗，只保证新失败记录按新逻辑落库。
3. 本次不修改知识库和面试评估链路，避免一次改造面过大。
