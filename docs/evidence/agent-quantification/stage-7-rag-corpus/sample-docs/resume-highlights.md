# 简历亮点表达规范

## 表达原则

简历亮点应围绕岗位匹配、问题难度、个人贡献和结果证据展开。好的简历不是把技术栈堆满，而是让面试官快速判断候选人解决过什么问题、承担过什么责任、产出了什么结果。每条亮点都应尽量包含动作和结果，例如“优化订单查询接口，将 P95 延迟从 600ms 降至 180ms”。

表达时要避免空泛词，例如“熟悉高并发”“负责系统优化”“参与核心项目”。这些词如果没有场景和证据，很难被复核。可以改成“基于线程池隔离和 Redis 缓存削峰，支撑活动页峰值 QPS 从 300 提升到 1200，错误率保持低于 0.1%”。

## 量化指标

常见量化指标包括延迟、吞吐、错误率、可用性、成本、人工效率、数据规模和用户规模。性能类可以写平均延迟、P95、P99、QPS、CPU 或数据库负载。效率类可以写处理时长减少、自动化覆盖率提升、人工步骤减少。稳定性类可以写故障次数下降、告警收敛或恢复时间缩短。

指标要注意口径真实。不要把压测峰值包装成线上稳定 QPS，不要把团队整体收益全部写成个人贡献。没有精确数字时，可以用范围或相对比例，例如“分钟级缩短到秒级”“减少约三分之一人工处理时间”。如果指标来自日志、监控或报表，应能在面试中说明来源。

## 项目描述结构

项目描述可以采用“背景 + 职责 + 方案 + 结果”的结构。背景说明业务问题，职责说明个人承担范围，方案说明关键技术动作，结果说明收益。每个项目不必写成长段落，简历上可以用 3 到 5 条 bullet 展示，但每条要有信息密度。

例如一个知识库 RAG 项目可以写：负责知识库上传、解析、向量化和检索调试链路；为 chunk 写入 sourceTitle、sectionTitle、chunkIndex 和 preview 元数据；构建固定语料和检索 debug 视图，支持后续 retrieval eval 复核。这样的表述比“实现 RAG 功能”更具体。

## 风险边界

简历不能夸大不具备的能力。没有接入公开 benchmark，就不要写“达到行业领先 RAG 水平”。没有做线上灰度和监控，就不要写“保障高可用”。如果只是 MVP，应写清楚“建立最小可复核评测集”或“补齐可解释检索证据”，不要包装成大规模生产检索平台。

对 AI Agent 项目尤其要注意边界。可以写工具调用、状态管理、guardrail、eval 和 trace；但如果没有自主长期规划、复杂多 agent 协同或公开基准验证，就不要使用容易被追问的夸大词。面试官会根据简历关键词深入追问，边界不清会带来信任风险。

## 改写示例

弱表达：“参与知识库模块开发，支持文档上传和智能问答。” 改写为：“负责知识库文档解析、向量化和 RAG 问答链路，补充检索 debug 信息，展示命中 chunk 的来源文档、section、顺序和预览，降低排查检索误命中的成本。”

弱表达：“熟悉并发编程，做过线程池优化。” 改写为：“针对异步任务积压问题，重设 ThreadPoolExecutor 核心线程数、有界队列和拒绝策略，增加队列长度与拒绝次数监控，使任务堆积告警从日均多次下降到可控范围。” 改写时要保证每个数字都能解释来源。
