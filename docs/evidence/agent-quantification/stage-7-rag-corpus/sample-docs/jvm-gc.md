# JVM GC 与内存模型

## 运行时数据区

JVM 运行时数据区通常包括堆、虚拟机栈、本地方法栈、程序计数器和方法区。堆用于存放大多数对象实例，是 GC 的主要区域。虚拟机栈保存栈帧，栈帧中有局部变量表、操作数栈、动态链接和方法返回地址。程序计数器记录当前线程执行位置，是线程私有区域。

面试回答中要注意区分 JVM 内存模型和 Java 内存模型。运行时数据区是 JVM 内部的内存布局，Java 内存模型描述多线程下共享变量的可见性、原子性和有序性规则。两者都和内存有关，但追问方向不同。

## 对象创建与逃逸

对象创建大致包括类加载检查、分配内存、零值初始化、对象头设置和执行构造方法。内存分配方式可能是指针碰撞或空闲列表，取决于堆是否规整。并发创建对象时，JVM 可以用 CAS 重试或线程本地分配缓冲 TLAB 降低同步成本。

逃逸分析用于判断对象是否只在方法内使用。如果对象没有逃逸到方法外，JIT 可能做栈上分配、标量替换或锁消除。面试中不应承诺所有短生命周期对象都会在栈上分配，因为这是优化结果，取决于 JVM 实现、代码形态和运行时编译。

## GC Roots 与可达性

Java 判断对象是否存活主要用可达性分析。GC Roots 可以包括虚拟机栈中引用的对象、方法区中类静态属性引用的对象、常量引用的对象、JNI 引用的对象和被同步锁持有的对象。从 GC Roots 出发能到达的对象被认为存活，不能到达的对象可以回收。

引用类型包括强引用、软引用、弱引用和虚引用。强引用存在时对象不会被回收；软引用适合缓存，内存不足时可能回收；弱引用下一次 GC 即可能回收；虚引用主要用于跟踪对象被回收的通知。回答缓存设计时，可以说明软引用缓存不适合做核心业务缓存，因为回收时机不稳定。

## 垃圾收集器

Serial GC 简单但会 Stop-The-World，适合小堆或客户端场景。Parallel GC 注重吞吐量，适合批处理。CMS 以低停顿为目标，但存在内存碎片和并发模式失败风险。G1 把堆拆成 Region，通过预测停顿选择回收集合，适合较大堆和可控停顿目标。ZGC 和 Shenandoah 进一步降低停顿，但需要结合 JDK 版本和业务验证。

选择 GC 时不要只说“低停顿就用 G1”。应先明确业务指标：吞吐量、P99 响应时间、堆大小、对象分配速率、Full GC 频率和容忍停顿。线上排查时要采集 GC 日志、堆转储、线程栈和应用指标，结合对象分配热点分析，而不是只调大堆。

## 常见问题排查

频繁 Young GC 可能来自对象分配速率过高、年轻代过小或短生命周期对象过多。频繁 Full GC 可能来自老年代增长过快、内存泄漏、元空间压力或晋升失败。内存泄漏排查通常先确认堆使用持续上升，再用 heap dump 比较对象数量和引用链。

OOM 类型需要具体判断。Java heap space 通常表示堆不足或泄漏；Metaspace 可能和动态生成类、类加载器未释放有关；Direct buffer memory 可能和 NIO 直接内存或 Netty buffer 释放有关；unable to create native thread 可能是线程数过多或系统资源不足。回答时要把现象、证据和处理动作连起来。
