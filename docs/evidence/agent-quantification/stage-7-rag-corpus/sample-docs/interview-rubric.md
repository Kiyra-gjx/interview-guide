# 面试回答评分 Rubric

## 评分维度

技术面试回答可以从准确性、结构性、场景化、边界意识和沟通质量五个维度评分。准确性关注概念是否正确、有没有明显错误。结构性关注回答是否有层次，例如先定义问题，再讲机制，最后讲实践。场景化关注是否能结合真实业务，而不是只背概念。边界意识关注是否知道方案适用条件和风险。沟通质量关注表达是否清楚、是否能回应追问。

高分回答通常不是最长回答，而是能够抓住问题核心。比如问 Redis 缓存穿透，合格回答能说出查询不存在数据导致请求打到数据库；更好回答会补充缓存空值、布隆过滤器、参数校验的适用场景和副作用；优秀回答还会说明如何监控空值命中率和异常 key 分布。

## 分档标准

一档回答存在明显概念错误或答非所问。例如把 volatile 说成能保证所有操作原子性，或者把缓存击穿和雪崩完全混淆。二档回答能说出名词但缺少机制，常见表现是罗列关键词却无法解释原因。三档回答能解释机制并覆盖基本场景。四档回答能结合工程实践、取舍和排查方法。五档回答能主动说明边界、指标和失败处理。

评分时要避免只看候选人是否说出某个固定术语。部分候选人可能不用标准名词，但能准确描述机制和解决方案，也应给合理分数。相反，只堆术语但无法落到场景的回答不应高分。Rubric 的目的不是机械扣分，而是让评价可复核。

## 追问设计

追问应该沿着同一主题逐步加深。基础题确认概念，例如“什么是 happens-before”。机制题确认原理，例如“volatile 为什么不能保证 count++ 原子性”。工程题确认经验，例如“线程池队列满了怎么办”。边界题确认判断力，例如“什么时候不该用缓存”。

好的追问会暴露真实理解。比如 MySQL 索引题可以从“联合索引最左前缀”追到“范围条件后的列还能不能用”，再追到“Explain 看到 Using filesort 怎么判断是否需要优化”。不要用偏门冷知识作为主要评价依据，除非岗位确实需要。

## 证据记录

面试评价应记录候选人的具体回答证据，而不是只写“基础一般”。可记录为“能解释线程池提交流程，但没有提到有界队列和拒绝策略风险”。这种记录能支持后续复盘，也能减少不同面试官之间的主观偏差。

如果候选人在追问后修正了答案，应记录修正过程。能够在提示后定位问题并修正，说明有一定推理能力；完全依赖提示才能说出结论，则说明知识掌握不稳定。评分要区分主动回答、轻提示回答和重提示回答。

## 常见误区

不要把项目包装能力和技术理解混为一谈。表达流畅但内容不准确不能高分，表达稍慢但推理清楚也不应低估。不要因为候选人使用不同技术栈就完全否定其能力，应关注底层原理和迁移能力。对初中级岗位，评价重点应是基础扎实和可培养；对高级岗位，重点应是系统性、取舍能力和故障处理经验。

Rubric 还应避免单题定生死。一次回答失误可能来自紧张或题目理解偏差，应通过多个维度交叉验证。最终结论最好包含优势、风险和建议级别，例如“Java 并发基础合格，系统设计缺少容量估算，建议进入下一轮但重点追问线上排障”。
