# Redis 缓存问题

## 缓存模式

缓存旁路模式是业务最常见的方案：读请求先查缓存，缓存未命中再查数据库，然后写回缓存；写请求先更新数据库，再删除缓存。删除缓存通常比更新缓存更稳妥，因为缓存值可能由多表聚合或复杂计算得到，直接更新容易写入不一致结果。

读写一致性要说明边界。先更新数据库再删除缓存仍可能出现短暂不一致，例如删除缓存失败或并发读把旧值写回缓存。工程上可以用重试删除、消息队列补偿、延迟双删或订阅 binlog 做异步修正。强一致场景不应只依赖普通缓存。

## 穿透、击穿、雪崩

缓存穿透指查询不存在的数据，请求绕过缓存持续打到数据库。常见处理包括缓存空值、布隆过滤器和参数校验。缓存空值要设置较短过期时间，避免大量无效 key 占用内存。布隆过滤器适合大集合存在性判断，但有误判概率，不适合返回完整数据。

缓存击穿指热点 key 过期瞬间，大量请求同时回源。处理方式包括互斥锁、逻辑过期、热点 key 永不过期加异步刷新。缓存雪崩指大量 key 同时过期或 Redis 集群不可用，引发数据库压力。处理方式包括过期时间加随机抖动、分批预热、多级缓存、限流降级和 Redis 高可用。

## 数据结构

String 适合简单 KV、计数器和分布式锁值。Hash 适合对象字段缓存，可以局部更新字段，但字段过多也会带来内存和维护成本。List 适合简单队列，Set 适合去重集合，Sorted Set 适合排行榜和按分数范围查询。Bitmap 适合签到和布尔状态集合，HyperLogLog 适合 UV 估算。

选择数据结构时要从访问模式出发，而不是先背命令。比如排行榜需要按分数排序、查询排名和 Top N，Sorted Set 比 List 更自然。用户标签去重和交并差适合 Set。高频计数要关注原子性和热点 key，可以用分片计数降低单 key 压力。

## 分布式锁

Redis 分布式锁的基础形式是 `SET key value NX PX ttl`，value 要唯一，用于释放时校验持有者。释放锁应使用 Lua 脚本保证“判断 value 和删除 key”的原子性。只用 setnx 再 expire 分两步可能在进程崩溃时留下无过期锁。

分布式锁的风险包括锁过期但业务未完成、客户端长 GC 暂停、网络分区和时钟假设。可以用续期机制降低长任务风险，但更重要的是让业务操作具备幂等性。面试中不要把 Redis 锁描述成绝对可靠的强一致锁，它更适合容忍有限风险的互斥场景。

## 性能与治理

Redis 性能问题常见来源包括大 key、热 key、慢查询、网络带宽和持久化压力。大 key 会导致删除阻塞、迁移慢和单次返回过大。热 key 会让单个节点压力过高，可以通过本地缓存、key 拆分、读副本或请求合并缓解。

线上治理要开启慢日志、监控命中率、内存使用、连接数、阻塞命令、过期 key 数量和 evicted keys。缓存命中率下降时要区分业务新增查询、过期策略不合理、key 设计变化和 Redis 故障。回答排查题时应先说观测指标，再说处理动作。
