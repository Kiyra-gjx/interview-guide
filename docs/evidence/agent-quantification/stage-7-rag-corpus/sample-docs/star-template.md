# 项目讲解 STAR 模板

## 模板目标

STAR 模板包括 Situation、Task、Action 和 Result，用于把项目经历讲成可验证的业务故事。Situation 描述背景和约束，Task 描述目标和职责，Action 描述具体动作和技术方案，Result 描述结果和指标。面试中使用 STAR 的目的不是套格式，而是让回答有上下文、有贡献、有证据。

项目讲解最常见的问题是只讲技术名词，不讲为什么做、自己做了什么、效果如何。比如“我做了缓存优化”太泛，应改成“在商品详情接口 P99 延迟升高到 800ms 的背景下，我负责把高频读数据引入 Redis 缓存，设计缓存旁路和失效补偿，最终把 P99 降到 180ms，并把数据库 QPS 降低 60%”。

## Situation 背景

背景部分应包含业务场景、用户规模、请求量、数据量、团队约束和历史问题。背景不需要很长，但必须让面试官知道问题为什么重要。例如“系统是内部后台”与“系统是峰值每秒数千次请求的 C 端接口”会影响方案评价。

背景描述要避免泄露公司敏感信息，可以使用量级和比例。比如“不说真实收入和客户名，可以说日均订单百万级、核心链路不可用会影响交易转化”。如果没有真实指标，可以说明当时观测到的现象，例如慢 SQL、接口超时、队列堆积或人工处理耗时。

## Task 职责

任务部分要讲清自己负责什么。团队项目中尤其要区分个人贡献和团队成果。可以说“我负责缓存 key 设计、接口改造和压测验证，DBA 协助建立索引，测试同学负责回归”。不要把团队全部成果包装成个人单独完成。

职责还应包含成功标准。比如“目标是在不改变业务语义的前提下，把查询接口 P95 降到 200ms 以下，并保证库存更新后 5 秒内缓存收敛”。有成功标准，后续 Action 和 Result 才能被验证。

## Action 动作

动作部分应按问题拆解讲方案。可以先说定位过程，再说关键改动，再说风险控制。比如性能优化可以讲“通过日志和 APM 发现瓶颈在订单聚合查询；用覆盖索引减少回表；对低频维表增加本地缓存；对热点用户增加 Redis 缓存；上线前做压测和灰度”。

技术动作要解释取舍。为什么用缓存而不是只加索引，为什么删除缓存而不是更新缓存，为什么用有界队列而不是无界队列。能讲清替代方案和放弃原因，通常比只说最终方案更有说服力。

## Result 结果

结果最好包含数字指标，例如延迟下降、错误率下降、吞吐提升、人工耗时减少、成本下降或稳定性提升。指标应有口径，例如平均值、P95、P99、峰值 QPS、样本周期。没有指标时，可以用可验证现象替代，例如“发布后两周没有再出现队列堆积告警”。

结果也要包含遗留问题和复盘。真实项目很少完美，说明后续计划反而更可信。比如“缓存方案解决了读压力，但强一致场景仍走数据库；后续计划通过 binlog 异步刷新减少删除缓存失败窗口”。面试官通常会追问结果是否可持续，因此要准备监控和回滚说明。

## 回答结构

一次完整项目讲解可以控制在 2 到 4 分钟。建议结构是：一句话概括项目价值，三句话说明背景和目标，三到五句话讲关键动作，一到两句话讲结果和复盘。被追问时再展开具体技术细节。不要在开头就陷入代码细节，否则面试官可能听不到项目价值。

常见追问包括“这个方案有什么风险”“如果 QPS 再涨十倍怎么办”“你怎么证明是你做的优化有效”“上线后出过什么问题”。准备 STAR 时应提前为每个项目准备这些追问答案。好的项目讲解不是背稿，而是有足够证据支撑自由展开。
