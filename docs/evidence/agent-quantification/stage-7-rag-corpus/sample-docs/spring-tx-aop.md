# Spring 事务与 AOP

## 事务代理机制

Spring 声明式事务通常通过 AOP 代理实现。调用被 `@Transactional` 标注的方法时，代理对象在方法执行前开启事务，在方法正常返回时提交，在抛出符合回滚规则的异常时回滚。默认情况下，运行时异常和 Error 会触发回滚，受检异常不会自动回滚，除非配置 rollbackFor。

事务失效的常见原因包括同类内部方法调用绕过代理、方法不是 public、目标类没有被 Spring 容器管理、异常被捕获后没有重新抛出、数据库引擎不支持事务，以及传播行为不符合预期。面试中要强调“代理对象”是关键，不是注解本身有魔法。

## 传播行为

REQUIRED 是默认传播行为，有事务就加入，没有就新建。REQUIRES_NEW 总是挂起当前事务并开启新事务，适合审计日志等希望独立提交的场景。NESTED 使用保存点实现嵌套回滚，依赖底层事务管理器和数据库支持。SUPPORTS 有事务就加入，没有事务就非事务执行。

传播行为追问通常考察边界。比如主订单创建成功后写操作日志，如果日志失败不应影响主事务，可以用 REQUIRES_NEW 并捕获日志异常。反过来，如果库存扣减必须和订单创建同生共死，应使用 REQUIRED 并让异常向外传播。

## 隔离级别

事务隔离级别用于处理脏读、不可重复读和幻读。READ_UNCOMMITTED 可能读到未提交数据；READ_COMMITTED 避免脏读；REPEATABLE_READ 避免不可重复读，MySQL InnoDB 默认级别通常是 REPEATABLE_READ；SERIALIZABLE 最严格但并发性能最低。

回答隔离级别时要结合数据库实现。MySQL InnoDB 通过 MVCC 提供一致性读，通过 next-key lock 在当前读场景下处理幻读风险。不要机械地说某个隔离级别一定完全消除所有场景的幻读，应该说明快照读和当前读的差异。

## AOP 切面顺序

Spring AOP 基于代理，JDK 动态代理面向接口，CGLIB 通过子类代理类。final 类或 final 方法不适合 CGLIB 代理增强。多个切面同时存在时，可以使用 `@Order` 控制顺序。事务切面、日志切面和鉴权切面混用时，顺序会影响日志记录的时机和异常捕获范围。

AOP 适合横切关注点，例如日志、监控、鉴权、事务和幂等校验。不适合把核心业务流程隐藏进切面，否则代码可读性和调试成本会变差。面试中可以说明 AOP 的收益是复用横切逻辑，但风险是调用链隐式化。

## 工程实践

事务方法中应避免长时间持有数据库连接，例如远程 HTTP 调用、大文件处理或复杂计算不应放在事务内。长事务会增加锁等待、连接占用和回滚成本。常见优化是先做参数校验和外部查询，再开启事务执行关键写入。

事务边界建议放在 service 层，controller 不直接管理事务，repository 只负责持久化细节。对批量写入要关注批大小、索引影响和失败补偿。涉及消息发送时，要考虑本地事务和消息一致性，可以用事务消息、outbox 表或补偿任务，而不是在数据库提交前直接发送不可回滚的外部消息。
