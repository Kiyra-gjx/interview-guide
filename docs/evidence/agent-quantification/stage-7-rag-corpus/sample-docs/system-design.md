# 系统设计：限流与缓存

## 设计目标

系统设计题首先要澄清目标：用户规模、QPS、读写比例、延迟要求、一致性要求、可用性目标和成本约束。限流与缓存不是独立技巧，而是服务稳定性设计的一部分。回答时应先说明保护对象，例如保护数据库、保护第三方接口、保护核心服务线程池或保护用户体验。

一个后端接口在高峰期变慢时，不应该只加缓存。要先判断瓶颈来自数据库查询、锁竞争、外部服务、CPU、网络还是连接池。缓存解决重复读和热点读，限流解决过载保护，降级解决非核心能力关闭，熔断解决依赖持续失败。

## 限流算法

固定窗口计数实现简单，但窗口边界可能出现流量突刺。滑动窗口把时间切成多个小窗口，统计更平滑。漏桶算法以恒定速率流出，适合平滑请求。令牌桶按固定速率生成令牌，允许一定突发流量，是接口限流中常用方案。

限流维度可以按用户、IP、租户、接口、应用实例或全局资源设置。单机限流实现简单但不能控制集群总量，分布式限流可以用 Redis、网关或专门限流组件。分布式限流要关注 Redis 延迟、脚本原子性和降级策略，不能让限流组件本身成为单点瓶颈。

## 缓存策略

缓存设计要明确 key 结构、value 格式、过期时间、更新策略和一致性边界。热点配置类数据可以较长 TTL 并支持主动刷新；用户状态类数据 TTL 应较短；强一致交易数据不应只靠缓存判断。缓存 key 要包含版本或租户维度，避免多环境、多租户数据串扰。

缓存预热适合确定的热点数据，例如首页配置、热门榜单和字典表。缓存淘汰要关注 Redis maxmemory-policy。allkeys-lru 可以淘汰任意 key，volatile-lru 只淘汰设置过期时间的 key。业务要避免关键 key 没有 TTL 或全部在同一时间过期。

## 降级与熔断

降级是在资源紧张或依赖异常时关闭非核心能力，例如关闭推荐、减少实时统计、返回默认配置。熔断是在依赖连续失败后短时间快速失败，避免请求堆积。限流、降级和熔断经常组合使用：限流挡住过量入口，熔断隔离失败依赖，降级保住主流程。

设计降级时要有明确的用户可接受返回。比如面试题推荐服务失败时，可以返回热门题或空列表；支付创建订单不能返回假成功。降级结果必须在产品和业务上可解释，不能为了技术稳定牺牲核心正确性。

## 观测指标

限流和缓存上线后需要监控命中率、限流次数、拒绝率、P95/P99 延迟、错误率、队列长度、线程池活跃数、数据库连接池使用率和 Redis 慢查询。只看平均延迟会掩盖尾延迟问题。限流阈值要根据压测、容量评估和线上指标逐步调整。

压测要区分单接口压测和链路压测。单接口压测能发现局部瓶颈，链路压测能发现依赖传播和资源竞争。压测前要准备隔离环境、数据规模、监控面板和回滚方案。面试中可以用“目标、容量、保护、观测、演练”的结构组织系统设计回答。
