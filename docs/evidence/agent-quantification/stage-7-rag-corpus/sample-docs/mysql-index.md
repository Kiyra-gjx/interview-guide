# MySQL 索引与事务

## B+Tree 索引

MySQL InnoDB 常用 B+Tree 索引。B+Tree 的非叶子节点存储键和指针，叶子节点按键有序并通过链表连接，适合等值查询、范围查询和排序。相比二叉树，B+Tree 扇出更高，树高更低，能减少磁盘 IO。面试中应说明索引提升查询速度的代价是占用空间、降低写入速度和增加维护成本。

聚簇索引的叶子节点保存整行数据，InnoDB 表通常按主键组织。二级索引叶子节点保存索引列和主键值，命中二级索引后如果需要其他列，会根据主键回表。覆盖索引指查询所需列都在索引中，可以避免回表。

## 联合索引

联合索引遵循最左前缀原则。索引 `(a, b, c)` 可以支持 `a`、`a,b`、`a,b,c` 的前缀查询，也可以在 `a` 等值后对 `b` 做范围。遇到范围条件后，后续列通常不能继续用于精确定位，但可能仍用于索引下推过滤。

设计联合索引要结合 where、order by 和 group by。高选择性列不一定永远放最前面，如果业务常按租户隔离，tenant_id 可能需要作为前导列保证查询范围可控。面试中可以用“查询模式优先，选择性辅助”的表述，避免只背“区分度最高放前面”。

## 索引失效

常见索引失效场景包括对索引列使用函数、隐式类型转换、前导模糊 like、or 条件不当、范围条件后列无法继续定位，以及统计信息不准导致优化器选择全表扫描。`where date(create_time)=...` 可能无法有效使用 create_time 索引，应该改成范围查询。

Explain 是判断执行计划的重要工具。常看字段包括 type、key、rows、filtered 和 Extra。type 从 const、ref、range 到 index、ALL 逐渐变差，但要结合数据量判断。Extra 中 Using index 表示可能覆盖索引，Using filesort 表示需要额外排序，Using temporary 表示使用临时表。

## 事务与锁

InnoDB 支持行锁，但行锁依赖索引。如果更新条件没有命中索引，可能扫描并锁住更多行，造成并发下降。锁类型包括记录锁、间隙锁和 next-key lock。next-key lock 是记录锁加间隙锁，用于在某些隔离级别和当前读场景下防止幻读。

MVCC 通过 undo log 和 read view 提供一致性读。READ COMMITTED 通常每次语句生成新的 read view，REPEATABLE READ 通常事务内复用 read view。当前读如 select for update、update、delete 会读取最新版本并加锁。回答隔离级别问题时要区分快照读和当前读。

## 优化实践

慢 SQL 优化流程通常是确认 SQL、查看执行计划、检查索引、评估返回行数、观察锁等待和 IO。不要一上来就加索引。加索引前要确认该索引能覆盖稳定的高频查询，并评估写入成本和冗余索引。重复索引和低价值索引会拖慢写入。

分页查询在大偏移时会变慢，因为数据库需要扫描并丢弃大量行。可以用基于游标的翻页，例如 `where id > last_id order by id limit n`。对于复杂列表，可以先用覆盖索引查主键，再回表查详情。面试中要说明优化目标是减少扫描行数、减少回表和避免额外排序。
