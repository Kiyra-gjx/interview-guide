# S2-03：Runtime Approval and Policy

## 0. 任务状态

- 状态：已完成
- 当前定位：Stage 2 已完成任务
- 前置依赖：S2-02 已完成

## 1. 任务目标

为高风险动作建立可解释、可追踪、可恢复的审批模型与策略边界。

## 2. 要解决的问题

- Guardrails 只能做基础阻断，还不能表达“可以执行，但必须先审批”
- 不同 Tool 或动作的风险等级缺少统一分类标准
- 系统缺少 `pending / approved / rejected / expired` 等审批状态语义
- 审批结果还不能稳定映射到执行恢复、终止或失败解释

## 3. 本任务范围

- 风险等级与审批策略定义
- 审批状态模型与接口语义
- 高风险动作进入审批后的运行时行为
- trace、状态与调试面中的审批结果表达

## 4. 主要改动点

- approval policy / risk level 模型
- 审批状态存储或状态表达层
- `interview.guide.modules.agent.service.AgentOrchestrator`
- Tool 执行前决策逻辑与恢复入口

## 5. 风险与边界

- 本任务不扩展到多步工作流引擎，也不引入 Stage 5 的 loop / handoff 语义
- 审批模型应只覆盖明确的高风险动作，避免把所有工具都变成必须审批
- 批准后的恢复行为必须确定，不能出现重复执行或状态漂移

## 6. 完成标准

- 高风险动作会进入明确的审批状态，而不是直接执行或直接丢弃
- 审批通过、拒绝、过期后，系统行为与终态语义清楚一致
- trace 能解释该动作为何需要审批、审批结果是什么、后续行为是什么
- 审批策略能按风险等级稳定复用，而不是散落在 if / else 中

## 7. 验证要求

- 至少覆盖 `pending`、`approved`、`rejected` 三类主流程测试
- 审批后的恢复或终止路径能被重复执行并保持一致结果
- 高风险动作在未审批状态下不能绕过策略直接执行
