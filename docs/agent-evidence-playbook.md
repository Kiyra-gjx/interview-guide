# Agent Evidence Playbook

## 1. 这份文档解决什么问题

这不是一份很长的测试教程，而是一份轻量 playbook，用来回答三件事：

- 每做完一段能力后，应该留什么证据
- 这些证据更适合用什么方式验证
- 最后怎样把这些结果沉淀成简历或项目叙事里的亮点

## 2. 先记住的原则

- 不要等项目全部做完后再临时补数据
- 比起单纯追求 QPS，更重要的是机制是否带来了可验证收益
- `Workbench / Demo Surface` 用于观察、调试、展示，不等于评测工具
- `Eval / Regression / Benchmark` 才是验证系统机制与回归稳定性的主链路
- 每次机制改造，至少保留一组“改动前 / 改动后”对照结果

## 3. 建议保留的三类材料

### 3.1 运行工件

- trace
- report
- session / checkpoint / resume 快照
- 关键日志、失败样例、审批记录

这类材料回答的是：“这一轮到底发生了什么”。

### 3.2 对照实验

- 改造前结果
- 改造后结果
- 相同任务集
- 相同预算或接近预算条件

这类材料回答的是：“这个机制到底有没有带来收益”。

### 3.3 固定回归集

- 固定任务清单
- 固定 verifier 或验收条件
- 固定输出记录方式

这类材料回答的是：“后续改动有没有把已经做好的东西弄坏”。

## 4. 每次做实验至少记什么

可以用下面这五项当最小模板：

- 目标：这次要证明什么
- 样例：用了哪些固定任务
- 条件：模型、预算、开关、审批模式、是否开启某机制
- 指标：成功率、失败率、重复调用次数、平均步数、prompt 长度等
- 输出物：trace、report、结果表、失败样本

## 5. 各阶段更适合测什么

### Stage 2：Safe and Observable Runtime

- guardrail 命中分布
- approval 状态分布
- 回归通过率
- 失败原因是否可解释
- trace / report 是否足够支撑复盘

### Stage 3：Domain Tooling and Context Assembly

- prompt 长度与裁剪稳定性
- 当前请求是否完整保留
- 重复工具调用次数是否下降
- 领域工具命中质量是否提升
- 输出归一化后回答链路是否更稳定

### Stage 4：Agent Workbench and Demo Surface

- demo 主路径是否稳定可复现
- workbench 是否能直接看到关键调试信息
- 失败、降级、拒绝等状态是否能被解释
- 用户视角与调试视角是否分层清楚

说明：
Stage 4 更像“展示与观察能力验收”，不是替代 Stage 2 的 eval 或 Stage 5 的 benchmark。

### Stage 5：Bounded Multi-Step Agent

- 预算内完成率
- 平均步数与停止原因分布
- 失败语义是否一致
- handoff / subagent 是否真的带来收益
- 恢复后是否误用旧状态或越过边界

## 6. 一个最小可用的做法

如果你之前没有系统测过，可以先按最小版本来：

1. 为每个 Stage 选 5 到 10 个固定样例。
2. 每次大改动前先跑一遍，记下基线结果。
3. 改完后在相同条件下再跑一遍。
4. 保留结果表和一组代表性 trace / report。
5. 如果结果变好，就记录收益；如果结果变差，就把它当成回归问题处理。

## 7. 最后怎样沉淀成亮点

最终能写进简历或项目介绍里的，通常不是“做了某机制”，而是：

- 这个机制解决了什么问题
- 它让什么指标发生了变化
- 这些结果是通过什么样例或评测路径验证的

所以更好的表述通常是：

- 不是“实现了 memory”
- 而是“通过分层记忆与相关记忆召回，把 follow-up 阶段重复读取已知信息的次数降下来，并用固定任务集验证收益”

- 不是“实现了 approval”
- 而是“通过 approval 与 guardrails，把高风险动作从直通执行改为受控执行，并能从 trace 与回归样例中解释命中原因与最终结果”

## 8. 使用建议

- roadmap 里只保留原则，不要把它写成教程
- Stage 文档里只保留本阶段最关键的证据类型
- 真正的结果表、样例清单和对照记录，可以按你后续习惯放进 `artifacts/`、`scripts/` 或单独的评测目录
