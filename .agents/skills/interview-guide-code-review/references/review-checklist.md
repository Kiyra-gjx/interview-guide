# 审查清单

## 1. API 契约与客户端兼容性

- 标准后端 JSON 接口通常应返回 `Result<T>`。
- `frontend/src/api/request.ts` 默认假设返回 `HTTP 200 + { code, message, data }`。
- 二进制下载/导出接口可以有意绕过 `Result<T>`，直接返回 `ResponseEntity<byte[]>`。
- 只要 diff 修改了响应结构、路由路径、字段名、枚举值或可空性，但没同步更新前端调用方，就要报风险。

## 2. 异步处理与任务状态

- producer 和 consumer 的改动要一起看。
- 确认状态流转仍然合理：`PENDING` -> `PROCESSING` -> `COMPLETED` 或 `FAILED`。
- 确认重试逻辑不会悄悄重复执行，或掩盖最终失败。
- 确认消息 ACK 时机正确，失败时仍会落下有价值的诊断信息。

## 3. AI Prompt 与结构化输出稳定性

- 在这个仓库里，prompt 改动不是单纯的文本改动。
- 检查要求的输出是否仍匹配 Java DTO / parser 的预期。
- 检查严格 JSON 指令、修复逻辑和重试行为在变更后是否仍然合理。
- 如果 prompt 让输出自由度变大，但解析器没有同步加固，要报风险。

## 4. 文件、存储与导出链路

- 上传/解析改动要保留文件校验、内容提取和清理行为。
- 存储改动要保持对象存储假设和配置一致。
- PDF / 导出改动要保留字节流响应、文件名处理和失败日志。

## 5. 错误处理与用户可见语义

- 优先沿用现有业务/AI 异常处理路径，不要到处写临时响应。
- 检查新增异常是否仍能转换成用户看得懂的错误信息。
- 注意那些原本返回 `Result.error(...)` 的流程，是否被改成直接漏出裸 `500`。

## 6. 测试与验证质量

- 验证范围要和风险等级匹配。
- 纯逻辑改动时，定向单测可能就够了。
- 契约改动时，只看后端编译不够；还需要前端构建或调用方检查。
- Redis / DB / 对象存储链路要明确说明是否只是部分验证。
